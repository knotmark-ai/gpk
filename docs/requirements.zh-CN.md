# 用户需求与场景

[English](requirements.md) 是主稿；本文辅助理解，场景编号与主稿保持一致。

这是 GPK 的目标需求清单，覆盖日常行动管理、知识管理及两者结合。它描述产品意图，
不表示场景已经全部实现。[当前支持](../README.md#current-support)负责能力现状，
[Roadmap](roadmap.md)负责交付顺序，[验收场景](conformance-scenarios.md)负责具体可观察行为。

## 什么才是场景

场景从输入或处境出发，说明用户要解决的问题及有用的结果。例如：“随手丢进一篇文章，
希望保留其中的解释，同时识别值得处理的待办。”

Setup、Skill、模板、标签、Adapter、同步都是可能的手段，不是用户的目标。需求证明
手段的必要性以后，再到设计文档里说明实现。一个需求可以涉及多个 Skill，一个 Skill
也可以服务多个需求。编号只用于追踪，不引入新的实体、必填字段或运行时分类模型。

不是每个行动都需要 Project 或 Objective/KR；不是每个 Source 都需要 Area、立即用途
或 Wiki 更新。候选行动不等于已接受的承诺。保存什么、执行什么由用户意图和授权范围决定。

## 1. 行动与项目

| 编号 | 处境与用户需求 | 期望结果 |
|---|---|---|
| ACT-01 | “周五前提交报销。”记录日常小事。 | 可找回的独立提醒，保留相关凭据与固定约束；不强行建立 Project。 |
| ACT-02 | 随手记录混杂且不清晰，需要判断是否行动。 | 区分已接受的行动、尚待澄清的记录、参考资料和未承诺的可能性；只问必要的问题。 |
| ACT-03 | “下一步做什么？”希望选出值得推进的事，而不是面对整个清单。 | 结合当前承诺、顺序和已知阻碍提供少量可选行动；不猜测无法感知的用户 Context。 |
| ACT-04 | 一个改变需要多个步骤，希望变成可完成的工作。 | 明确且有边界的 Objective、初始结果型 KR，以及按实际投入能力制定的计划；用户知道的信息直接询问，真实证据缺口才调研。 |
| ACT-05 | 长期方向需要多个 Project，希望看见完整的可能计划。 | 同时看见当前工作和未来候选；日期到来或前项完成不自动激活后项，也不代表允许执行。 |
| ACT-06 | 行动等待他人或外部条件，需要跟踪。 | 保留等待原因和合适的跟进；真实阻碍解除后再推进，不把阻塞工作当作可立即执行。 |
| ACT-07 | 延误、投入能力变化或假设失效，需要重新安排。 | 说明取舍并调整剩余范围、顺序、时间或 KR；保留已完成工作、历史和固定外部约束。 |
| ACT-08 | 项目看似完成，需要判断是否达到了目标。 | 用真实结果评估 KR，明确处理剩余行动并保留完成依据；勾选数量不等于目标实现。 |
| ACT-09 | “以后可能做。”希望留住可能性但现在不承诺。 | 想法或候选可以找回，但不挤入当前可执行推荐；已接受行动的推迟可以只调整计划时间。 |
| ACT-10 | 重复责任或习惯需要持续跟进，不想反复手工建提醒。 | 能力支持且获得授权时创建或呈现后续工作，不意味着工作已经完成；不支持自动化时明确说明。 |

ACT-10 是可选扩展，不是核心工作流的前提。它不要求自建服务器定时器或重型 Habit 模型。

## 2. 知识与参考资料

| 编号 | 处境与用户需求 | 期望结果 |
|---|---|---|
| KN-01 | 保存网页、论文、书、视频、讲座或课程，以后找回并理解。 | 可追溯出处、可检索摘要及符合用途的材料；不要求一律全文导入。 |
| KN-02 | 材料复杂或语言不熟悉，需要相应深度的理解。 | 根据要求摘要、翻译、精读或留档；明确实际可访问、实际读到的范围。 |
| KN-03 | 已有相关材料，但记不清标题，需要找回。 | 按主题和关系找到有用记录与证据，并说明检索覆盖限制。 |
| KN-04 | 多份资料讨论同一主题，希望形成理解而不是摘要堆。 | 持续维护主题解释，综合证据、区别、不确定性及 Source 链接。 |
| KN-05 | 新资料补充或反驳已有知识，需要更新认识。 | 以可追溯证据修改相关论断；保留分歧与不确定性，不静默抹掉它们。 |
| KN-06 | 概念越来越多，需要看清关系与独立知识点。 | 有用的链接与综述；独立概念必要时拆开，不规定固定卡片大小或独立 Index 实体。 |
| KN-07 | 保存联系人、人物、公司或产品调研，希望复用资料。 | 可检索的主题记录，包含相关事实、出处与关系；可以是普通 Wiki 主题，无需新实体类型。 |
| KN-08 | 遇到搬运、翻译、剪辑或评论，需要分清证据身份。 | 区分同一作品的不同版本与引用别人的独立作品；保留实际访问版本，尽可能找回原始出处。 |
| KN-09 | 有价值材料目前没有 Project 或 Area，需要先留住。 | 保存有用描述、主题和出处，让未来规划或调研能够发现，不编造当前用途。 |
| KN-10 | 旧笔记需要重命名、移动、合并或整理，希望安全完成。 | 保留有用内容、身份及关系；不确定的合并或冲突明确呈现，不直接丢弃。 |

## 3. 行动与知识结合

| 编号 | 处境与用户需求 | 期望结果 |
|---|---|---|
| COM-01 | 随手丢进 Source，可能包含知识、提醒或机会，需要判断用途。 | 可用于知识、产生 Task/Project 建议，或只保留 Source；建议与已接受行动分开。 |
| COM-02 | 规划目标或下一步，需要利用已有认知并发现缺口。 | 找到相关 Source、Wiki 和既往结果；区分向用户询问的已知事实与需要研究的外部证据。 |
| COM-03 | 阅读中产生想法或实验，希望不丢失下一步。 | 带着出处保留思考并提出适当后续行动；不把所有有趣段落变成承诺。 |
| COM-04 | 一份材料服务多个目的，希望复用而不割裂证据。 | Source、Wiki、Project 之间保持多对多关系和共同溯源；Agent 找到的材料也能融入同一知识。 |
| COM-05 | 执行 Task/Project 得到新信息，希望保存并回流。 | 简短结果可留在 Task 中；可复用发现更新合适的知识或计划，不自动新建 Wiki/Output。 |
| COM-06 | 已有知识能帮助决策、解释、产物或日常使用，希望用起来。 | 形成有依据的回答、决策、博客、脚本或其他结果；学习和查询也是使用，不局限于发布。 |
| COM-07 | Agent 对话里有有用决策和认知，希望沉淀下来。 | 可访问对话作为 Source；区分建议、确认、撤回和实际执行，补充相关知识或工作。 |
| COM-08 | 材料或会话跨 Session 持续变化，不想重复手工导入。 | 经授权自动及增量摄入新增/修订信息，不重复已完成效果；明确访问范围、溯源与执行限制。 |
| COM-09 | 优先级与证据变化，需要定期校准。 | daily、weekly、monthly 按适当范围检查承诺、结果和长期方向，提出有依据的调整；不必每次检查全部内容。 |
| COM-10 | 一个阶段或 Project 结束，需要决定如何继续。 | 结合实际结果与长期愿景/责任，启动、修改、调整归属或停止后续 Project；提前写好的阶段不是固定路线。 |
| COM-11 | 已有 Craft 工作空间、Obsidian 库或其他笔记集合，希望使用 GPK 而不是从头开始。 | 渐进整理选定材料，保留可追溯原件、有用链接和结果；恢复当前工作而不重新激活历史承诺，说明未决内容和实际覆盖范围。 |
| COM-12 | 日常或历史 Agent 会话包含决策、行动和认知，希望恢复关联完整的记录，无需手工复制讨论。 | 保留有用会话摘要，关联相关 Project，结合当前事实核对已接受行动和有证据的进度，维护可复用 Wiki，并从对应 Daily Notes 链接这些结果。 |

COM-08 包含启用后**自动沉淀选定 Agent 会话**的产品功能，不增加 Source 类型或业务
Skill；用户无需自己创建和维护一个周期业务任务来让它工作。这与“每天根据 Session
更新周报”这种明确业务节奏的用户自动化，以及可选的循环 Task/Habit（ACT-10）不同。
[架构原则](architecture.md#user-automation-versus-internal-feature-processing)负责实现与
调度选择；只保存启用标记或调度配置，不能证明实际沉淀或按要求的业务节奏交付。

### COM-11：把已有知识库整理到 GPK

初期设计提供两种选择：保留原知识库或经过验证的备份，在新目标工作空间导入；或者将
原工作空间整理成所选 Backend 的 GPK 表达方式。修改前预览方案并确认授权范围。
自动学习并兼容任意旧布局留作后续方向；允许用户指定位置和模板不等于承诺这种能力。

两种选择都复用同一个 [Ingest 逻辑](workflow-design.md)，一次执行或分批执行；区别是
输入范围、目标位置和原件保留策略，不新增 Migration Skill 或领域实体。旧文档作为
输入，识别其中的作品/证据并登记或复用 Source。身份跟随作品/证据，而非文件、主题或
产出去向的数量：

- 一篇自写旧笔记即使混合了计划、Tasks 和结论，也可以是一个 Source，支持多个目标
  实体；不能仅因用途不同拆成多个 Source。
- 单纯汇编多个独立文章的文档可以识别出多个 Source。同一作品的纯搬运、翻译保持
  共同身份并保留实际访问溯源。引用的作品不自动导入，也不因此宣称已经读过原文。

保留实际历史结果和当前人工修改，不重新激活旧 Task，也不从原文推导新授权。
经授权整理时，不确定旧材料留在可恢复的 Backup/Unsorted，不删除或硬分类。
重复或修订输入走增量 Ingest 和恢复逻辑，不重复创建 Source 和目标记录。明确切换并
验证后，以选定目标为当前领域事实的权威；原件/备份只是恢复证据，不是第二份现行
事实，也不隐式双向同步。Setup 本身不执行历史导入。

### COM-12：Agent 会话沉淀为行动、知识与每日记录

会话记录作为 Source 输入，复用同一 Ingest，不新增 Session 实体或 Conversation Sync
Skill。可独立识别的一个 Session 通常对应一个持续更新的 Source；新增消息、摘要、导出
和重复读取不产生新身份。不同 Session 不因属于同一 Project 就合并。留存深度由获授权
用途和隐私偏好决定；只拿到部分上下文时明确说明，不能称为完整逐字记录。

在已批准的会话范围和下游写入权限内，Ingest 可以自动：

- Prepare 有用摘要，保留决策、进度、未决问题和下一步。
- 将相关片段关联到明确选定或可清晰识别的当前 Project。一个 Session 可以支持多个
  Project；匹配不清晰时请用户作简短选择，无关讨论可以保持未归属。
- 为已接受行动创建 Task，依据实际证据更新已有 Task。建议、意图和完成声明保留各自
  归属，不能仅凭它们认定承诺或完成；同一任务反复提及不重复创建。
- 有依据时更新独立可复用的 Wiki 解释，不为每个 Session 新建 Wiki，也不整段堆入摘要。
- 在 Daily Notes 写入有日期的活动摘要及已验证链接，关联 Source、相关 Project、Task、
  结果和 Wiki 更新。这是导航与历史记录，不是第二份可编辑待办清单或状态权威。

按活动发生日期和实例时区归入 Daily Notes，不把延迟导入自动算作今天的活动。
时间未知时保留不确定性；跨午夜 Session 可关联两天记录，但不因此增加 Source。
增量重跑不重复创建记录或日志条目，也不覆盖人工修改。生成的摘要不会自动作为新证据
重新摄入，避免自我循环。

自动执行需要可用且获授权的会话读取器、Agent 执行环境、受支持触发器和可写目标。
不假定所有客户端/会话均可读取，或已有定时器运行。Project 匹配未决、Daily Notes
不可用和目标部分写入失败分别报告。每日摘要也不能代替 daily/weekly/monthly Review。

历史 Session 是这一需求的**历史回填变体**：从选定且可访问的来源、会话或日期范围，
恢复有用的既往决策、工作和认知。一次或分批复用同一 Ingest，不新增 Historical Sync
Skill 或另一套 Source 模型。保留实际先后关系和原始活动日期，不把导入日期当工作日期。

历史承诺先作为有归属的历史保留，只有确认当前相关性和状态以后才转为当前行动。
提出行动或更新进度前读取目标的最新事实，不因导入旧对话重复创建旧 Task、重新激活
已完成/已取消 Project，或用早期讨论覆盖后来决策。明确的历史 Project 可以关联，但不
改变状态；不确定关联保持未决，不强行归入当前工作。

说明已处理、排除、无法访问及未决范围，分批进度与实际效果保存在 Backend 以便恢复。
按获授权的隐私与 Prepare 范围保留出处；读取历史不意味着允许删除原件。重复导出、
重叠批次和之后的增量续接复用同一 Source 身份及处理依据。手工历史导入成功不证明
每日自动汇总或定期执行已经可用。

## 4. 贯穿所有场景的需求

| 编号 | 用户需求 | 期望结果 |
|---|---|---|
| SYS-01 | 换会话、受支持 Agent、设备或知识库后继续工作。 | 当前事实、关系和有用结果仍可从选定权威存储恢复；说明受支持环境与迁移限制。 |
| SYS-02 | 始终尊重个人语言、偏好和文档布局。 | 当前相关偏好和用户模板指导执行，不重复要求 Setup，不在更新时覆盖个人选择。 |
| SYS-03 | 直接在笔记软件里修改，然后让 Agent 继续。 | 读取最新事实、尊重人工修改，呈现冲突或过期写入，不依赖旧对话状态。 |
| SYS-04 | 请求中断或失败，需要可靠恢复。 | 区分已完成、失败与未知效果，保留有用的部分结果，不盲目重复成功操作。 |
| SYS-05 | 希望 Agent 帮忙，但保留控制权。 | 遵守授权范围，澄清重要决策和缺失权限；Source 中的文字不能授权。 |
| SYS-06 | 各工具能力不同，需要知道究竟做到了什么。 | 披露无法访问、不支持及覆盖不完整之处；不换成隐蔽权威，也不把建议说成保存成功。 |
| SYS-07 | 从私人知识系统产出公开成果，需要公私分明。 | 公开成果自包含，不依赖私人笔记或携带个人背景；私人记录可以向外链接成果。 |

可移植性是需求，不是首发支持所有环境的承诺。首期仍是 Codex、Claude Code 与 Craft；
后续环境逐项验证。方法应无需新的 GPK 托管服务、替代编辑器或中央知识镜像即可工作。

## 6. 一个贯通的例子

用户有一个正在推进的 Project，丢进一篇论文，问“有什么可用的？”：

1. 理解可访问材料，说明覆盖限制。
2. 查找已有相关证据、解释及当前 Project 决策。
3. 按要求保留可追溯 Source 与合适的 Prepare 结果。
4. 解释论文改变了什么、支持什么、仍有哪些不确定性。
5. 有需要则建议实验或下一步；不静默把建议变成已接受行动。
6. 在授权范围内更新相关知识或 Project 信息。
7. 后续实验结果回流到计划和可复用认知。

同一 Source 可以支持多个 Wiki、Project；也可以只作为参考，不产生行动或 Wiki 更新。
用户不必先指定目录、Skill 或 Area，系统才能提供帮助。
