# 写入工具自建命名空间，系统模板劝人从零开始

> 调研日期 2026-10-11。本报告综合五份研究笔记（Obsidian/Logseq 插件、Notion/Craft/Tana/Capacities 集成、Notion 付费模板、Obsidian 知识库系统、迁移实践），为 GPK 的"新建隔离空间 vs 融入用户既有结构"决策提供参照。英文引文保留原文；标注【待核验】的条目仅来自搜索摘要或三方转述，未直接抓取原文。

把 AI 或自动化内容写入既有个人知识库的工具，几乎一律选择**"自有命名空间 + 低摩擦暂存区 + 只在用户显式触发时才改既有内容"**：Readwise 默认写 `Readwise/`，Copilot 写 `copilot/`，Obsidian Web Clipper 写 `Clippings`，Craft API 新建文档落内置 `unsorted`，Notion MCP 无父级时落工作区级私有页，Tana 导入则直接开一个独立 workspace。**没有任何厂商发布过"集成应新建专用容器还是复用用户结构"的正式指引**，可观察到的事实惯例是五条：写前读取既有 schema、让用户在配置时选定目标容器、无目标就落产品暂存区、自己打来源标记（因为平台的 `created_by` 归属元数据不可靠）、不碰用户 schema 的高风险部分。付费系统模板在实体层高度收敛——Tasks→Projects→Areas/Tags 是共同主干，Goals 一律独立建库，Ultimate Brain 明文规定 "Tasks don't relate directly to Goals or Milestones—only Projects do."——但在状态编码（文件夹即状态 vs `status` 属性）与任务模型（行内 checkbox vs 每任务一条记录）上分叉，且 2025-08 Obsidian Bases 公开发布后明显向"属性编码"倾斜。对"已有内容怎么办"，模板作者的默认答案是从零开始：Ultimate Brain 把 Start fresh 列为 "no.1 recommended path"，Tiago Forte 主张 "Move all existing files to a folder titled 'Archive' with today's date"，Nick Milo 要求先独立开 vault 再把旧笔记搬进干净的 Ideaverse Zero，Zettelkasten 与 GTD 社区则把旧库当作只读 inbox 按需消化。对 GPK 而言，"新建隔离空间"拥有最多产品先例，但 Craft 的 Space 边界（"You can link another document or block inside the same Space."）使 Space 级隔离的代价远高于文件夹级隔离；"融入既有结构"在元数据层有 Capacities/Tana 的类型匹配算法可借，但在内容放置层没有任何产品敢替用户自动决定目录语义。

## 一、写内容的工具自建命名空间，写元数据的工具才适配用户分类

### 落点：无明确父级时一律落暂存区

跨产品的共同模式是"无父级 → 低摩擦暂存区 → 用户事后整理"。Readwise Obsidian 插件源码的 `DEFAULT_SETTINGS` 写死 `readwiseDir: "Readwise"`，设置文案是 "By default, the plugin will save all your highlights into a folder named Readwise" ([obsidian-readwise src/main.ts](https://raw.githubusercontent.com/readwiseio/obsidian-readwise/master/src/main.ts))。Copilot 的 "Copilot folder location"（默认 `copilot`）"keeps conversations, prompts, memory and more. All sub-folders derive from this." ([Copilot Settings](https://docs.obsidiancopilot.com/settings/))。Smart Connections 把索引写进 `.smart-env/`，并要求从第三方同步排除，因为它是 "generated index state, can create unnecessary writes and conflicts, and can be rebuilt on each device" ([Smart Environment FAQ](https://smartconnections.app/smart-environment/faq/))。Web Clipper 默认目录是 "Clippings"，用户可在模板的 "Note location" 改成 `01_Inbox/Clippings` 这类 inbox 子目录 ([Obsidian Forum #96186](https://forum.obsidian.md/t/obsidian-web-clipper-set-default-folder/96186))。

云端产品同样如此。Notion MCP 的 `notion-create-pages` 工具规定 "If a parent is not specified, a private page will be created." ([Notion Developers: MCP Supported tools](https://developers.notion.com/guides/mcp/mcp-supported-tools))；工具 schema 的完整描述进一步说明这些页面 "are created as standalone, workspace-level private pages, and the person that created them can organize them later as they see fit"【待核验，引自三方 MCP 目录】。值得注意的是 Notion 公共 REST API 对不同令牌类型的差异："For internal connections, a page or data source parent is currently required in the API."，而公共连接和 PAT 可省略 parent 直接 "creating a private page at the workspace level" ([Notion API Reference: Create a page](https://developers.notion.com/reference/post-page))——这等于 Notion 强制内部集成作者在设计时就决定"落到用户哪个页面/数据库"。Craft API 把位置定义为 "A location is either a folder or one of the built-in locations: 'unsorted' (default for new documents), 'templates' ..., or 'trash'"【待核验，[Craft API docs: Space](https://connect.craft.do/api-docs/space) 抓取被阻止，内容来自搜索摘要】；三方 craft-cli 的 `craft ls [--location unsorted|trash|templates|daily_notes]` 与 craft-auto-routing 专门 "Fetch the list of documents with `location=unsorted`" 再按置信度移入文件夹，侧面印证 `unsorted` 是集成写入的事实暂存区 ([alexpriest/craft-cli](https://github.com/alexpriest/craft-cli)；[ucpr/craft-auto-routing](https://github.com/ucpr/craft-auto-routing))。Tana Input API 规定 "Nodes will be placed in Library by default, unless targetNodeId is specified" ([tanainc/tana-input-api-samples](https://github.com/tanainc/tana-input-api-samples))；Capacities API 提供 `POST /blocks/daily-note/append`，官方把日记当作非结构化输入的缓冲区："jot things down as plain text, and promote them to typed objects later when you're ready." ([Capacities Docs: Switching from Tana](https://docs.capacities.io/migration/switching-from-tana))。

**只有 Notion AI Meeting Notes 把"落点"做成了面向终端用户的二选一设置**：在 Settings → Notion AI 的 "Default meetings database" 中选既有数据库或新建一个，之后 "the page will automatically be created inside your default database." ([Notion Help: AI meeting notes](https://www.notion.com/help/ai-meeting-notes))。这是调研范围内厂商对"复用用户既有结构 vs 新建专用容器"最直接的产品化。

### 命名空间还是适配：取决于写的是内容还是元数据

写内容的工具（Readwise、Clipper、Copilot、Smart Connections）几乎一律强加自身命名空间，把适配工作下放为三件可配置物：根目录名、文件名模板、frontmatter 模板。Readwise 提供 Jinja2 文件名模板与可自定义的 YAML Properties 区块（变量含 `{{title}}`、`{{author}}`、`{{url}}`、`{{category}}`、`{{document_tags}}`）([Readwise Docs: Obsidian](https://docs.readwise.io/readwise/docs/exporting-highlights/obsidian))。相反，写元数据的 AI 打标签类插件走的是适配路线：AI Tagger Universe 提供 Generate New / Predefined Tags（匹配 vault 已有 tags）/ Hybrid / Custom 四种模式 ([AI Tagger Universe](https://community.obsidian.md/plugins/ai-tagger-universe))，Smart Tagger AI "prefers existing tags in your vault to keep your taxonomy consistent" ([Smart Tagger AI](https://community.obsidian.md/plugins/onegayi-smart-tagger))。差别的根源在于：**tags 的取值空间可以从 vault 直接枚举，而目录归属没有等价的可枚举信号**，所以内容写入类工具无法安全判断用户目录语义，只能退回命名空间。

命名空间策略的用户侧代价有两条实证。一是"目录墓地"：论坛帖称 heavy clippers 常留下 `Readwise/Books/`、`Clippings/`、`Glasp/` 等 "created once during setup, then quietly forgotten as graveyards" 的默认目录 ([Obsidian Forum #114212](https://forum.obsidian.md/t/how-do-you-decide-where-a-clipped-note-belongs-before-it-lands/114212))。二是"搬不动"：Copilot 曾有五个独立目录设置，用户抱怨整体移动 `copilot/` 会 break 插件，提议合并为单一根目录并自动检测重命名，维护者 2026-08 标为 "not planned"，但现文档已改为子目录由根目录派生 ([obsidian-copilot issue #2432](https://github.com/logancyang/obsidian-copilot/issues/2432))。另有一派用户明确抵触工具写入专有属性：已停更的 Projects 插件的设计原则是 "The plugin must not leave any plugin-specific configuration in the notes, such as custom front matter properties." ([marcusolsson/obsidian-projects](https://github.com/marcusolsson/obsidian-projects))。

### 来源标记普遍薄弱，平台归属元数据靠不住

**几乎没有工具写专门的 "generated-by" 键。** Readwise 源码中 "No Readwise-specific frontmatter"，身份映射放在插件数据 `booksIDsMap`（文件路径 → Readwise book ID）而非文件内 ([obsidian-readwise src/main.ts](https://raw.githubusercontent.com/readwiseio/obsidian-readwise/master/src/main.ts))。Web Clipper 默认模板的 `source: {{url}}`、`created: {{date}}`、`tags: clippings` 是最接近"来源标记"的默认字段【待核验，官方帮助页未逐条列出，来自 [Sascha Kasper guide](https://sascha-kasper.com/step-by-step-guide-to-the-obsidian-web-clipper/)】。Logseq 的 gpt3-openai 插件用 "Inject Prefix" 在输出前注入 `[[gpt3]]` 标签或 `>` 引用块标记生成内容 ([logseq-plugin-gpt3-openai README](https://raw.githubusercontent.com/briansunter/logseq-plugin-gpt3-openai/master/README.md))。Capacities 是少数在导入流程里提供显式 marker 的产品："Block" 选项 "adds a text block to imported notes"，"Tag" 选项 "adds the selected tag to every imported object" ([Capacities Docs: Bulk Import Reference](https://docs.capacities.io/reference/bulk-import))。

Notion 的平台级归属机制看似可用，实则条件苛刻。用户对象 `type: "bot"` 代表集成并出现在 `created_by`/`last_edited_by` 中 ([Notion API Reference: User](https://developers.notion.com/reference/user))，但归属显示取决于令牌类型："Internal connections use their bot identity, public connections act for the user who authorized them, and PATs act as the user who created the token."【待核验，源应为 [Notion Developers: Authorization](https://developers.notion.com/docs/authorization)】。MCP 则 "act with your full Notion permissions"，以连接用户身份操作 ([Notion Help: Notion MCP](https://www.notion.com/help/notion-mcp))。**结论是：用 `created_by` 过滤集成产出只对内部连接稳定可行；产品若想可靠识别自己的产出，必须自己写属性/标签。** Craft 侧则完全空白——Craft Assistant 帮助页只说明它能 "add and replace content, apply styling, reorganize sections, create pages, move content, delete"，不含任何区分 AI 内容的标记说明 ([Craft Help: Craft Assistant](https://support.craft.do/hc/en-us/articles/8104602502557-Craft-Assistant))；Craft MCP 帮助页与 Craft Agents OSS 文档同样未提供标记指引 ([Craft Help: MCP](https://support.craft.do/en/integrate/mcp)；[Craft Agents OSS: Craft MCP Server](https://mintlify.wiki/lukilabs/craft-agents-oss/integrations/mcp/craft-mcp))。

### 覆盖保护的两种范式：外部哈希比对 vs 文件内所有权标记块

对既有内容的改动，所有工具都是"用户显式定位"模式：光标插入、Replace、Apply、heading/block/frontmatter 定向 PATCH，没有工具会主动重组用户现有笔记。真正值得借鉴的是两套防覆盖机制。

**Readwise 式（外部状态 + 哈希比对 + 追加）**：文档对外承诺 "the highlight will be _appended_ to the bottom of the existing page. Because the Readwise plugin is append-only, nothing in Obsidian will ever be overwritten." ([Readwise Docs: Obsidian](https://docs.readwise.io/readwise/docs/exporting-highlights/obsidian))。源码的实际逻辑比文档更细：已存在文件若本地哈希等于服务端 `last_content_hash` 则整体覆盖；哈希不同（用户改过）则追加 `existingContent.trimEnd() + "\n" + data.append_only_content` ([obsidian-readwise src/main.ts](https://raw.githubusercontent.com/readwiseio/obsidian-readwise/master/src/main.ts))。这套方案对用户零负担，但对改名脆弱——文档明确警告重命名或移动已同步文件后新高亮会生成重复文件；双向更新不支持，因为 "technically challenging to update highlights without accidentally overwriting user edits" ([Readwise Docs: Obsidian](https://docs.readwise.io/readwise/docs/exporting-highlights/obsidian))。

**Zotero Integration 式（文件内持久化标记块）**：默认 "Each time you import data from the same Zotero entry, it will overwrite the existing markdown file."，但模板里写 `{% persist "identifier" %}...{% endpersist %}`，输出文件中以 `%% begin identifier %%` / `%% end identifier %%` 包裹的区域在重导入时保留；另有 `isFirstImport`、`lastImportDate` 变量支持增量 ([Zotero Integration Templating.md](https://raw.githubusercontent.com/mgmeyers/obsidian-zotero-integration/main/docs/Templating.md))。这对改名鲁棒，但需要用户在模板里声明哪些区域是自己的。

API/MCP 层则提供了并发原语：Obsidian Local REST API 的 PATCH 支持 `If-Match` 乐观锁、`Reject-If-Content-Preexists`、`Create-Target-If-Missing`，并 "refuses to read or write any file inside Obsidian's configuration directory" ([obsidian-local-rest-api README](https://raw.githubusercontent.com/coddingtonbear/obsidian-local-rest-api/main/README.md))；obsidian-mcp 的 `obsidian_create_note` "Atomically establishes new notes without overwriting existing ones"，`if_match` etag 冲突触发 `REVISION_CONFLICT`，删除默认移入 `.obsidian-mcp/trash` ([obsidian-mcp README](https://raw.githubusercontent.com/StevenStavrakis/obsidian-mcp/main/README.md))。Notion 侧的对应物是 Autofill 的指令级保护——"If you only want to fill blank cells, add: 'Only fill this property if it is empty.'" ([Notion Help: Autofill](https://www.notion.com/help/autofill))——以及 Zapier 的反面案例："Multi-select property updates overwrite existing values instead of appending to them." ([Zapier Help: Notion on Zapier](https://help.zapier.com/hc/en-us/articles/8496102470541-How-to-get-started-with-Notion-on-Zapier))。

### Schema 驱动产品：先读结构再写，不碰高风险 schema

Tana、Capacities、Notion 三家对"已有非结构化内容"都选择**隔离 + 渐进**而非强制迁移，并且都把"写前读 schema"做成了 API 一等能力。Tana Input API 要求用 supertag/field 的 ID 写入，须先在标签上运行 "Show API schema" ([tanainc/tana-input-api-samples](https://github.com/tanainc/tana-input-api-samples))；Notion 导入落到 "a **new Tana workspace**, giving you a clean environment to explore and reorganize it without impacting your main system"，再靠 "Allow content from" 跨 workspace 引用、用 "Move with finder" 逐步合并 ([Tana Blog: Importing your Notion workspace](https://outliner.tana.inc/blog/importing-your-notion-workspace-into-tana-how-to-move-your-knowledge-into-a-more-flexible-connected-system))。Capacities 的 `GET /space/structures` 返回 "structures visible in the space, including property definitions and collections" ([Capacities OpenAPI](https://api.capacities.io/openapi.json))；其批量导入的类型匹配链是一个可直接借用的算法模板：frontmatter `type` 属性 → 文件夹名（"both singular and plural matches"）→ 用户选的 fallback object type ([Capacities Docs: Bulk Import Reference](https://docs.capacities.io/reference/bulk-import))。Capacities 还明确要求迁移前 "Define key object types early (`People`, `Projects`, `Meetings`, etc.)"，非名词性页面要么重构，要么 "imported as unstructured Pages without properties" ([Capacities Docs: Import From Notion](https://docs.capacities.io/migration/import-from-notion))。

Notion 自家 AI 划出的边界尤其值得参照：Autofill "Notion AI can create new databases but can't edit existing databases."（schema 层面，只填属性值）([Notion Help: Autofill](https://www.notion.com/help/autofill))；Notion Agent 能 "Create and edit databases"，但 "can't... Create new database automations, database templates, database page layouts, or advanced properties like formulas, rollups, or buttons" ([Notion Help: Notion Agent](https://www.notion.com/help/notion-agent))。**厂商自己也把"修改用户 schema 的高风险部分"排除在 AI 写权限之外。** Craft 的连接范围设计——Full Space Access / Daily Notes / Custom（"select one or more specific documents to include"），"everything else in your workspace" 保持私有，"Each connection is linked to a single space" ([Craft Help: MCP](https://support.craft.do/en/integrate/mcp))——是同一精神在授权层的体现。

## 二、付费模板的实体收敛，但状态编码与任务模型分叉

### 实体与关系：Task→Project→Area 是共同主干，Goals 一律独立

成熟付费系统普遍收敛到几乎相同的实体集。下表汇总可公开核实的部分。

| 系统 | 核心实体 | 必选关系 | Goals 表示 | 来源 |
|---|---|---|---|---|
| Ultimate Brain 3.0（$129） | Tasks, Projects, Notes, Tags（兼 Areas/Resources）, Goals, Milestones, People, Books, Work Sessions, Recipes | Task→Project（单一 Relation）；Project→Tag；Project→Goal | 独立库，三态 Dream/Active/Achieved；Progress 由 Milestones 完成比例计算；"Tasks don't relate directly to Goals or Milestones—only Projects do." | [UB Docs](https://thomasjfrank.com/docs/ultimate-brain/)；[Goals](https://thomasjfrank.com/docs/ultimate-brain/databases/goals/) |
| Easlo Second Brain（$39–99） | Projects, Tasks, Notes, References, Areas, Goals, Key Results, Topics, Highlights | 未公开 | Goals + Key Results 两个独立库 | [easlo.co](https://www.easlo.co/templates/second-brain) |
| Notion Everything 3.5（$64） | Areas, Projects, Tasks, Goals, Notes, Resources, Topics, Contacts + 4 bonus | 未公开 | 独立库 | [notioneverything.com](https://www.notioneverything.com/notion-second-brain) |
| Forte Labs 官方（$65） | Inbox, Projects, Areas, Resources, Archive, Daily Pages, Weekly Review, Habit Tracker | 未公开 | 无独立 Goals；2019 博文版本只有 Resources 建数据库 | [buildingasecondbrain.com](https://www.buildingasecondbrain.com/notion-template)；[fortelabs 2019](https://fortelabs.com/blog/how-to-build-a-second-brain-in-notion/) |
| PPV（课程，候补中） | Pillars, Pipelines（Value Goals→Goal Outcomes→Projects→Actions）, Vaults | 概念层 | Value Goals（年度）→ Goal Outcomes（类 OKR，季度/月度） | [esilva.net](https://esilva.net/tla_insights/ppv_bradley) |
| Notion 官方 Projects & Tasks | Projects, Tasks（±Sprints） | "each task should only relate to a single project" | 另有 OKR 指南：Objectives + Key Results 两库，KR 带 Initial/Current/Target Value 公式 | [Notion Help](https://www.notion.com/help/guides/getting-started-with-projects-and-tasks)；[OKR](https://www.notion.com/help/guides/how-to-create-okrs) |

两点值得注意。第一，**Ultimate Brain 用单个 Tags 库兼任 PARA 的 Areas 与 Resources**，以一个 Type 属性区分，并支持 Sub-Tags 层级（"Set Resource pages to be 'within' an Area page"）；文档注明 2024-11 之前该库叫 Areas/Resources ([UB Tags](https://thomasjfrank.com/docs/ultimate-brain/databases/tags/))。这是对 PARA 的扁平化实现，与 Easlo/Notion Everything 把 Areas、References、Topics 拆成独立库形成对照。第二，Goals 与 Projects 的区分被 UB 写得很明确："Goals, in contrast to Projects, are aspirational and may not have a specific path toward achievement that you can perfectly map out right now." ([UB Goals](https://thomasjfrank.com/docs/ultimate-brain/databases/goals/))，而 Notion 官方 OKR 指南只说 "You can neatly link your OKR database in other Notion pages"，未给出与 Projects & Tasks 库连接的具体步骤 ([Notion Help: How to create OKRs](https://www.notion.com/help/guides/how-to-create-okrs))。

Obsidian 阵营对 Goals 的建模明显弱于 Notion 阵营。被调研的系统里只有 marska 的 GTD vault 显式建模目标（`40-horizons — areas, goals, vision, purpose`）([marska/obsidian-gtd-vault](https://github.com/marska/obsidian-gtd-vault))；ACE 的"目标"隐含在 Efforts 强度和 `Calendar/Compass`（"keep your plans & reviews"）中 ([LYT Blog: Flexes For You](https://blog.linkingyourthinking.com/notes/the-ace-folder-framework-flexes-for-you))；PARA 社区模板只要求 "Define goals: Establish a goal for each project; reassign unclear items to Areas"，不单独成实体 ([byarbrough/obsidian-para](https://github.com/byarbrough/obsidian-para))；Zettelkasten 与 kepano 不建模目标。**没有任何 Obsidian 系统给出 goal→project 的 frontmatter 字段约定或查询示例。**

### 状态编码：文件夹即状态 vs `status` 属性，Bases 时代倒向后者

Obsidian 系统分三种编码。**文件夹即状态**：ACE 的 Efforts 按四强度分文件夹，On 🔥 "For the most active efforts & projects"、Ongoing ♻️、Simmering 〜 "For back of mind efforts"、Sleeping 💤 "For everything else (random, done, cold storage, etc)"，状态变化即移动文件夹——"Too much going on? Move an effort from `On` to `Simmering`." ([LYT Blog: Four Intensities](https://blog.linkingyourthinking.com/notes/the-four-intensities-of-efforts))；GTD vault 的 "A project's folder location indicates status: active (10-), parked (20-), or archived (90-)" ([marska](https://github.com/marska/obsidian-gtd-vault))；PARA 的 Projects→Archive 移动。**属性编码**：brianspo 套件的 `type: project` + `status: active|complete|archived|waiting` + `last-updated` ([brianspo/knowledge-vault-starter-kit](https://github.com/brianspo/knowledge-vault-starter-kit))；Bases 项目模板的 `status`（To Do / In Progress / Focus / On Hold / Cancelled / Completed）+ `progress` 0–100 + `deadline` ([Obsidian Forum #104249](https://forum.obsidian.md/t/a-bases-template-for-project-tracking-or-task-management/104249))。**零 frontmatter**：已停更的 Projects 插件以文件夹或 Dataview 查询定义集合。

时间线揭示了趋势。Bases 于 2025-05-21 随 1.9.0 进入 early access，2025-08-18 随 1.9.10 公开发布，"turn any set of notes into a powerful database"，"backed by your local Markdown files and properties stored in YAML" ([Obsidian changelog 1.9.10](https://obsidian.md/changelog/2025-08-18-desktop-v1.9.10/))；Projects 插件作者 2025-05 宣布停更、2025-07-18 归档仓库 ([marcusolsson/obsidian-projects](https://github.com/marcusolsson/obsidian-projects))。Obsidian CEO Steph Ango 的 vault 则是属性路线的极致："I avoid folders because many of my entries belong to more than one area of thought."，用 `categories` 属性 + 每类一个 `.base` 取代文件夹，规则包括 "Always pluralize categories and tags"、"Default to `list` type properties instead of `text`"、"Property names and values should aim to be reusable across categories" ([stephango.com/vault](https://stephango.com/vault))。文件夹编码的优点是零插件、拖拽即改状态；缺点是无法同时表达"类型"和"状态"两个维度，所以 PARA/GTD vault 常再叠一层 frontmatter。Notion 阵营没有这个分叉——Status 属性是唯一选择，UB Projects 的 Status 取值为 Planned / On Hold / Doing / Ongoing / Done，另有 Archived 复选框使其从主仪表盘消失 ([UB Projects](https://thomasjfrank.com/docs/ultimate-brain/databases/projects/))。

### 任务绑定与"下一步行动"：行内 checkbox 与每任务一条记录互斥

Notion 系统的任务绑定是单一 Relation。UB Tasks 的 Project 为单一 Relation；"下一步行动"由 Smart List 公式决定，"possible values (in priority order): Calendar, Do Next, Delegated, Snoozed, Someday, Inbox"，配合 My Day 复选框（"Marks tasks for today's execution"）与 Wait Date（"Tracks delegated task follow-up"）([UB Tasks](https://thomasjfrank.com/docs/ultimate-brain/databases/tasks/))。从优先序可推断：有 Due 日期→Calendar；否则按手选 Smart List；有 Snooze→Snoozed；全空→Inbox 即"未处理"（这是推断，文档未逐字给出公式）。UB 2025-01 删除了 GTD Contexts，改为 Energy / Location / P-I 三个日计划属性，并改用 Notion 原生 Sub-Tasks ([UB Changelog](https://thomasjfrank.com/docs/ultimate-brain/changelog/))。

Obsidian 系统存在两种互斥的数据模型。Dataview 时代的主流是 **"任务是项目笔记里的 `- [ ]` 行，列表是查询"**：marska 的口号是 "One source of truth: tasks are lines in notes, lists are queries."，核心标签 `#next`/`#waiting`/`#tickler` 加上下文标签，8 个 dashboard 含 "60 Stalled Projects" ([marska](https://github.com/marska/obsidian-gtd-vault))；alangrainger 的 `tasks.js` 识别没有下一步的项目并支持 task sequencing，作者认为 "GTD implementations are quite specific...It's hard to modify a plugin, and impossible to cover every use case." ([alangrainger/obsidian-gtd](https://github.com/alangrainger/obsidian-gtd))。Bases 时代出现 **"每任务一笔记 + `related_project` 属性"**：cauenapier 的方案 "every task can be a self contained note, not just a single line"，属性含 priority, effort, due_date, status (ToDo/Done), depends_on, related_project, done_date，紧急度公式 priority×2 + 日期×3 ([cauenapier: Tasks in Bases](https://cauenapier.com/blog/tasksinbases/))。两者互斥的原因是 Bases 只索引 note-level properties，不解析行内 checkbox。"停滞项目"（项目存在但无 `#next` 任务）查询在三个 GTD 实现中都出现，甚至有专门插件 ([saibotsivad/obsidian-gtd-no-next-step](https://github.com/saibotsivad/obsidian-gtd-no-next-step))——这是 GTD 类系统的核心健康检查，GPK 的 Project/Task 模型若要支持 review，应能回答同样的问题。

### 捕获到处理：Inbox 是一等实体，处理靠"打上归属即离开 Inbox"

所有系统都把 Inbox 做成一等实体，但"离开 Inbox"的判定不同。UB 的入门三习惯是 "Capture new tasks to the Inbox"、"Once a day, sit down and check over your Tasks section"、为捕获项设置 Projects 与 Due Dates；笔记同样 "Capture new notes to the Inbox" 后加 Tags 或 Projects ([Start Using UB the Simple Way](https://thomasjfrank.com/docs/ultimate-brain/start-using-ultimate-brain-the-simple-way/))——即**归属关系为空就是 Inbox**。Forte 官方模板的口号是 "Capture ideas, notes, links, and tasks in seconds. Process them later when you're ready." ([buildingasecondbrain.com](https://www.buildingasecondbrain.com/notion-template))；2019 博文版本是 "Create an Inbox page, a parking spot for random notes." ([fortelabs 2019](https://fortelabs.com/blog/how-to-build-a-second-brain-in-notion/))。Obsidian 系统用带前缀的文件夹：GTD vault 的 `00-inbox`，PARA+CODE 的 `00 - Inbox` + `05 - Clippings` 并要求 "Clear `00 - Inbox` weekly" ([brianspo](https://github.com/brianspo/knowledge-vault-starter-kit))，ACE 社区实现的 `+` 前缀文件夹（第三方对 `+` 的语义描述不一致：一说 "Quick capture inbox"，一说存放非知识/非日历/非项目的支持内容）([yanickfischer](https://github.com/yanickfischer/obsidian-ACE-method-skills)；[lobehub](https://lobehub.com/skills/mrfelton-ideaverse-ideaverse))。Nick Milo 的总原则是 "Do less now. I strongly encourage deferring any 'great customizations' for later"，"structure must be earned" ([LYT Blog: ACE](https://blog.linkingyourthinking.com/notes/ace-folder-framework))；他刻意用 "efforts" 而非 "projects"，因为 "'projects' smother creativity and development by forcing too much structure too early." ([LYT Blog: Why Efforts are Liberating](https://blog.linkingyourthinking.com/notes/why-efforts-are-liberating))。

### 归属标记：没有通用约定，文件夹位置仍是最低成本的隔离

若一个工具要在用户 vault 中可靠区分"本系统管理的笔记"，**现有生态里没有通用约定**。最接近的先例是 brianspo 的 `type:` 与 kepano 的 `categories:`；Ideaverse 社区实现用 `up`/`in`/`related`/`collection` 关系属性而非系统归属标记 ([yu-wenhao LYT guide](https://yu-wenhao.com/en/blog/lyt-framework-guide/))；Obsidian 官方只定义了 `tags`、`aliases`、`cssclasses` 三个默认属性 ([Obsidian Help: Properties](https://obsidian.md/help/properties))。Bases 的过滤语法支持 `file.inFolder("...")`、`file.hasTag("tag")`、`file.hasLink("...")` 及任意属性比较 ([Obsidian Help: Bases syntax](https://obsidian.md/help/bases/syntax))，意味着"把系统笔记放进专属文件夹"仍是最低成本且与 ACE/PARA/GTD 习惯兼容的隔离方式。未找到任何系统使用命名空间化属性（如 `gpk_type`、`system: lyt`）——这是空白而非未搜到。

## 三、模板对"已有内容"的指引：从零开始是默认，迁移靠归档与按需拉取

**只有 Ultimate Brain 与 Forte Labs 官方模板给出了成文的迁移指引**，其余系统（Easlo、PPV、Pascio、Notion Everything、Notion 官方模板）对既有内容基本沉默，仅说明复制到 Private 或 Teamspace。UB 2.0→3.0 迁移指南给出三个选项——Do nothing / Start fresh（"no.1 recommended path"）/ Transfer——理由是 "transferring data is possible, but time-consuming and error-prone"，并借势 "start 2025 with a beefed up, clean system"；Transfer 路径需要给新旧库加 "[UB - OLD]" / "[UB - NEW]" 后缀、在 "Transfer Center" 建 Linked Views、改旧库属性匹配新库、先测一个库再全量、手动恢复所有关系，官方声明 "this process is complex, can be time-consuming, and is something we can't provide active support on." ([UB Transfer Guide](https://thomasjfrank.com/docs/ultimate-brain/transfer-guide/))。UB 的哲学是 "let your tools follow your workflow, not the other way around"，但其 Simple Way 页面未规定模板放 Private 还是 Teamspace ([Start Using UB the Simple Way](https://thomasjfrank.com/docs/ultimate-brain/start-using-ultimate-brain-the-simple-way/))。行业默认是"复制模板到一个新顶层页面"，既不建新 workspace，也不导入既有数据库；UB 的 Transfer Center 实质是 Linked View 集合 + Notion 原生"移动到数据库" + 手工修关系。

Forte 的立场最激进也最一致。最简版是 "How to organize your digital life in under 60 seconds: Move all existing files to a folder titled 'Archive' with today's date. That's it! Your digital workspace is now completely clean so you can start over" ([Tiago Forte on X, 2023](https://x.com/fortelabs/status/1650424401983152128))；2019 博文对既有 Notion 内容的处理是把剩余 blocks 全部移到 "ARCHIVE – {Today's Date}" 页 ([fortelabs 2019](https://fortelabs.com/blog/how-to-build-a-second-brain-in-notion/))；对 read-later 积压则是 "Declare Read Later Bankruptcy" ([Tiago Forte on X, 2020](https://twitter.com/fortelabs/status/1259322850835525633))。fortelabs.com 的 PARA 主文经抓取确认**没有**讨论既有材料处理；"归档后按例外只救回 1%"的说法仅见于聚合站转述 ([Taskade](https://www.taskade.com/blog/the-para-method))。官方 Notion 模板声称有 "Extensive migration guide walks you through bringing in your existing notes"，覆盖 "another Notion setup or tools like Evernote, Apple Notes, or Google Docs"，但细节在付费墙内 ([buildingasecondbrain.com](https://www.buildingasecondbrain.com/notion-template))。

Nick Milo 走的是**"以套件为主、旧笔记为客"的 Zero 模式**：Ideaverse Pro "needs to be opened as a separate vault"，推荐流程是 "Download Ideaverse Pro first. Explore. Play around. Identify what you like most. Then download Ideaverse Zero and transfer your notes into it." ([Ideaverse Pro](https://www.linkingyourthinking.com/ideaverse-pro))；从旧 ACCESS 结构迁到 ACE 的建议是 "Just put `Cards`, `Sources`, and `Special` under `Atlas` for now" ([LYT Blog: A deeper dive](https://blog.linkingyourthinking.com/notes/a-deeper-dive-into-how-ace-works))；2025 年视频描述更直白："No folders, no imports, no pressure. Just five notes, one simple prompt" ([PKM Weekly 2025-04-06](https://www.pkmweekly.com/p/pkm-weekly-2025-04-06))。PARA 社区模板则是**"旧笔记为客、按需提升"的 Archive-first 模式**：第一步 "Create a dated folder in `4. Archive` and move all existing folders there intact"，之后 "Move archived notes to proper locations as you use them"，原则 "Avoid bulk sorting; instead, migrate notes reactively during workflow"，并警告 "Avoid pre-creating empty folders in Resources" ([byarbrough/obsidian-para](https://github.com/byarbrough/obsidian-para))。两种模式都回避"原地合并"，与第三方对 Ideaverse 合并风险的警告一致："A direct full merge can create duplicate filenames, broken relative links, conflicting properties, and theme or plugin settings that you have not reviewed." ([obsidianmate](https://obsidianmate.com/vaults/ideaverse))。

GTD 与 Zettelkasten 社区把旧材料当作**只读 inbox/来源**。GTD 论坛面对巨量积压的共识不是"全部处理"，而是隔离：Gardener 说 "When you're overwhelmed your default should be Someday/Maybe, and as an exception, a RARE exception, move some to your current lists"，mcogilvie 说 "Work to keep today's inputs under control. Keep your lists short while you are building habits" ([GTD Forum #15500](https://forum.gettingthingsdone.com/threads/how-do-you-even-actually-implement-gtd-when-youre-so-deep-in-the-overwhelming-chaos.15500/))。Zettelkasten 论坛对"800 条旧笔记是否转入"的主流回答是不要批量转换：Sascha 对"把旧系统当作 inbox 逐步消化"直接回答 "Yes"，并说 "I filter strongly. I ditch what I don't understand with reasonable effort"；Sepuku 建议 "3 zettels (even if they are 1 liners) a day" ([Zettelkasten Forum #1467](https://forum.zettelkasten.de/discussion/1467/what-do-i-do-with-my-hundreds-of-notes-i-have-outside-of-zettelkaesten)；[#937](https://forum.zettelkasten.de/discussion/937/processing-old-notes))。工具厂商的官方建议同向：Tana "import some sections or databases at a time, instead of your entire workspace" ([Tana: Import data](https://outliner.tana.inc/learn/features/import-data-into-tana))，Capacities 先清理、先子集试导、分批导入 ([Capacities: Import from Notion](https://docs.capacities.io/migration/import-from-notion))，Reflect 建议导入前新建独立 graph ([Reflect Academy](https://reflect.academy/import-export-backups))。

三派在"不要让旧材料阻塞新系统启动"上完全一致，差别只在旧材料的角色：PARA 把它当冷存储（默认永不回看），Zettelkasten/GTD 当待处理来源（有需求才拉取），Nick Milo 当需要搬进新结构的客体。**没有一派主张在既有结构上原地叠加新系统。** 唯一例外是 Marie Poulin 的免费 Daily Meeze 模板含 "instructions for plugging in your existing databases" ([notionmastery.com/templates](https://notionmastery.com/templates/))，以及 alangrainger 建议把核心脚本 "integrate ... into existing vaults incrementally" ([alangrainger](https://github.com/alangrainger/obsidian-gtd))——两者都是组件级而非系统级接入。

## 四、多空间并行的硬限制与迁移的技术性失败模式

隔离到独立空间的代价在 Craft 上有官方文档可查。"Each Space acts as a separate workspace with its own documents and Space-level settings."，跨 Space 移动文档时 "Block links are preserved, but shared links and comments are lost" ([Craft Help: Working with Spaces](https://support.craft.do/en/introduction/account-setup/spaces))；链接范围被限定为 "You can link another document or block inside the same Space." ([Craft Help: Links and Backlinks](https://support.craft.do/en/organize-and-find/linking))；搜索是唯一跨 Space 的能力："Global Search finds results across all spaces and documents." ([Craft Help: Search](https://craft-support.mintlify.app/en/organize-and-find/search))。MCP/API 连接 "Each connection is linked to a single space" ([Craft Help: MCP](https://support.craft.do/en/integrate/mcp))。用户评价称 "it's really clunky to move things between spaces, search between spaces, etc., and you also cannot create backlinks to files in other spaces"【待核验，原始评论页未能定位】。**这意味着若 GPK 开独立 Space，GPK 写入的 Project/Source 将无法 @-引用用户旧 Space 里的任何文档，反向亦然。**

Obsidian 多 vault 的论坛实证指向同样的结论。Austin 因 "the friction to switch from one vault to the other to put something in the right place was too much" 而出现知识图谱缺口并回到单 vault；AntonVS 列出嵌入链接迁出后断裂、"Two instances of Obsidian can't be opened at once"、多设备同步复杂；RyanMiller 的建议是 "you could just create a project folder in the same vault" ([Obsidian Forum #1445](https://forum.obsidian.md/t/one-vault-vs-multiple-vaults/1445)；[#20272](https://forum.obsidian.md/t/how-to-use-daily-notes-when-you-have-multiple-vaults/20272))。论坛共识倾向"一个 vault + 文件夹/标签隔离"，除非有合规或工作-个人等强边界需求（Kenobimienjung："a Zettelkasten belongs in its own vault"）。Tana 是唯一把"导入即新 workspace"做成默认的产品，但它同时提供 "Allow content from" 跨 workspace 引用机制来补偿——Craft 没有等价物。

迁移本身的技术性失败模式被官方承认。Notion 导入 Evernote "Reliable up to ~5,000 notes. Larger imports may fail."，且 "Imports add rows. They don't update existing rows, so watch for duplicates."，日期 "may appear incorrect" ([Notion Help: Import data](https://www.notion.com/help/import-data-into-notion))；Logseq 导入 Roam "All dates and times are not preserved upon import" ([logseq issue #4644](https://github.com/logseq/logseq/issues/4644))；Craft 导入 Notion "you have to add every page individually and cannot select the entire workspace at once"，"Linked (mirrored) database views will be skipped." ([Craft Help: Import from Notion](https://support.craft.do/en/import-and-export/import/notion))。Provenance 保留普遍薄弱：Obsidian 官方 Notion 导入器写 `notion-id` 属性 ([obsidian-importer issue #676](https://github.com/obsidianmd/obsidian-importer/issues/676))，第三方 notion2obsidian 做得更完整——"Generates YAML metadata including: Notion IDs for reference" 并补 "Creation & modification dates: Real document timestamps" ([bitbonsai/notion2obsidian](https://github.com/bitbonsai/notion2obsidian))。**若新系统需要可靠的原创建时间或回指原条目的引用，必须自己写属性，不能依赖导入器。** 渐进迁移的实际节奏也很低频：John 用 datetime 检查点文件倒序转换，"every now and then I seem to scroll by it, and then convert a few notes" ([Zettelkasten Forum #937](https://forum.zettelkasten.de/discussion/937/processing-old-notes))。开源 agentic-PKM 项目给出了"legacy 为只读来源"的精确先例：标记为 `verification_state == "legacy"` 的笔记 "are excluded from search under normal operations because the Obsidian vault has no scope, provenance, or verification" ([RasmusTho/agentic-pkm-mvp issue #5933](https://github.com/RasmusTho/agentic-pkm-mvp/issues/5933))。

## 五、面向 GPK 设计决策的对照

GPK 要向 Craft 写入 Project / Area / Task / Source / Wiki / Output 六类实体，本节把可行方案与上文证据对齐，列出取舍，不替用户决定。

| 方案 | 先例 | 支持证据 | 代价/风险 |
|---|---|---|---|
| **A. 新建独立 Craft Space** | Tana 导入即新 workspace；Nick Milo "needs to be opened as a separate vault"；Zettelkasten 独立 vault 派 | 零污染用户既有结构；GPK 可完全掌控 Collections schema、文件夹与 Daily Notes；Craft 连接本身 "linked to a single space"，授权边界天然清晰 | Craft 链接 "inside the same Space" 的硬限制使 GPK 的 Source/Wiki 无法 @-引用旧 Space 文档，Project 无法反链用户已有笔记；Tana 有 "Allow content from" 补偿，Craft 没有；Obsidian 多 vault 实证显示"放哪"的摩擦导致图谱缺口并最终回归单空间；每日捕获入口分裂 |
| **B. 同一 Space 内的 GPK 专属文件夹/Collections** | Readwise `Readwise/`、Copilot `copilot/`、Clipper `Clippings`、ACE/PARA/GTD 的前缀工具文件夹、Bases 的 `file.inFolder()` 隔离 | 调研范围内写内容类工具的绝对主流；保留 Space 内链接与反链；Craft `GET /folders` 可发现既有结构；与用户用 PARA/ACE 时"并列新建系统文件夹"的习惯一致 | "目录墓地"风险（用户遗忘的默认目录）；根目录改名/移动需鲁棒（Copilot #2432、Readwise 重命名产生重复的反例）；需自建归属标记，因 Craft 没有 `created_by` bot 身份也没有 AI 内容标记 |
| **C. 融入既有结构（写入用户已有文件夹/Collections）** | Notion AI Meeting Notes 的 "Default meetings database" 可选既有库；Capacities `/space/structures` + 类型匹配链；Tana "Show API schema" 后按 ID 写入；AI 打标签插件的 "Predefined Tags" 模式；Marie Poulin "plugging in your existing databases" | 元数据层可行：读 Collections schema、匹配既有类型，Capacities 的 frontmatter type → 文件夹名 → fallback 是现成算法；避免"两套 Projects" | 内容放置层无先例：没有任何产品自动决定用户目录语义，只有 craft-auto-routing 这类事后分类器（带置信度阈值）；Notion Agent/Autofill 自身都不改既有 schema 的高风险部分；UB 迁移经验表明属性映射"time-consuming and error-prone"且需手工修关系；Zapier multi-select 覆盖是反面案例 |
| **D. 混合：GPK 专属容器 + 读取既有结构 + 旧内容只读引用** | Readwise 单向 append-only；PARA "dated Archive + 按需提升"；Zettelkasten "旧库当 inbox"；agentic-pkm 的 `legacy` 状态排除出默认检索 | 把 B 的隔离与 C 的 schema 读取结合；旧内容不迁移、不修改，GPK 实体通过 Craft 块链接引用它（同 Space 内可行）；按需 "promote" 为 GPK 实体时记录来源 ID（类 `notion-id`） | 实现复杂度最高；"按需提升"在实证里节奏很低频，需要 review 流程主动推动；要定义 promoted-from 字段与只读边界 |

几条跨方案的设计点在证据里反复出现，无论选哪条路都要回答。**落点**：无父级时需要一个暂存区，Craft 已内置 `unsorted`【待核验】，是否复用它还是建 GPK Inbox 文件夹，对应 UB"归属为空即 Inbox"与 Obsidian `00-inbox` 两种编码。**来源标记**：Craft 无平台级 AI 归属，GPK 必须自写标记；可借的形态是 Clipper 式属性字段（`source`/`tags`）、Capacities 式导入 marker（block 或 tag）、Logseq 式块级前缀；Projects 插件 "must not leave any plugin-specific configuration in the notes" 代表的抵触意味着标记应可选或可配置。**覆盖保护**：Readwise 的"哈希相同才整体覆盖、否则只追加"与 Zotero 的 `%% begin/end %%` 持久块是两种成熟范式，Local REST API 的 `If-Match` 与 obsidian-mcp 的 etag 是 API 层原语；Craft API 是否提供版本/etag 本次未核实。**Schema 边界**：Notion Agent 不建 automations/templates/formulas/buttons、Autofill 不改既有 database schema，是厂商自己划的"AI 可写"红线，GPK 对用户既有 Collections 的改动范围可参照。**状态编码**：Notion 阵营一律 Status 属性，Obsidian 阵营正从文件夹迁向属性；Craft 的文件夹与 Collections 属性并存，GPK 选哪种会决定用户能否"拖拽改状态"。**Goal 挂载**：UB "only Projects do" 的显式决策与 PPV 的 Value Goals→Goal Outcomes→Projects→Actions 链路是两个可对照的 Objective/KR 建模参考。

## 结论

调研最反直觉的发现是：**"隔离"在产品层几乎是唯一被实现过的策略，而"融入"只在元数据层（tags、schema 匹配）有先例，在内容放置层是空白**——不是因为厂商没想到，而是因为目录语义无法被枚举，任何自动放置都是在替用户做分类决定。与此对应，方法论作者无论流派都劝人从零开始，但他们的"从零"实际上是"旧内容冻结为冷存储或只读来源、新系统只处理新输入、旧内容用到才拉"，这与 Readwise 式单向 append-only 同步在结构上同构。GPK 面对的真正二选一因此不是"新 Space 还是旧 Space"，而是"隔离的粒度"：Craft 把链接范围锁在 Space 内，使 Space 级隔离比 Obsidian 多 vault 还要硬（后者至少有 `obsidian://` URI），文件夹级隔离则继承了插件生态十年来最成熟的那套惯例（可改名根目录、自带来源字段、显式触发才改既有内容）。

另一条隐含的结论是时间维度：Bases 公开发布一年多以来，Obsidian 阵营正在把"类型与状态"从文件夹搬进属性，Projects 插件因此停更；Notion 阵营从一开始就是属性编码。这意味着 GPK 若把 Project/Task 的状态编码在 Craft Collections 属性而非文件夹位置，会与两个阵营的收敛方向一致，也更容易支撑"停滞项目"这类 GTD 核心查询——但要以放弃"拖拽改状态"的零学习成本为代价。证据的最大缺口在 Craft 自身：官方 API 文档未能抓取，`unsorted` 默认落点、是否有 etag/版本锁、Daily Notes 是否按 Space 隔离都待核验；在做最终决定前，这三项应直接对照 Craft API 原文确认。
